# 11. 漏洞发现侧：Anthropic OSS Scanner

**来源：** [sorrycc 2026-10 梳理 §11](https://research.sorrycc.dev/@sorrycc/2026-10-security-incidents)  
**可信度：** 已确认（Anthropic 官方说明与发布文章；团队成员 Punit Shah 公开线程）

## 概况

Anthropic 于 **10-08** 推出 OSS Scanner，为关键开源项目免费定期漏洞扫描。截至 **10-20**（上线约 11 天），团队公布：约 **650** 项目申请，**114** 被接收，向维护者报告 **77 Critical + 803 High**。等级由**模型评定**，≠ 人工确认漏洞数；被接收项目尚未全部扫完。

## 典型案例：curl CVE-2026-92392

- HTTP/2 上传中断后悬空指针 → UAF。9-15 提交，curl 团队数小时内确认；curl **8.23.0** 修复（发布周期从 8 周缩短到 6 周）。
- Daniel Stenberg：描述一条 RCE 路径但条件苛刻（受害者向攻击者控制且持有效证书的服务器上传约 135KB，可用载荷约 23 字节）；认为最可能只是崩溃；同时对报告与复现材料质量评价很高。

## 项目机制（官方）

- 核心维护者向 `anthropics/oss-scanner` 提 PR 申请，参照 OSS-Fuzz 标准审核。
- 常规 CVD 有人工复核；截至 10 月已复核 **6,000+** 份报告。
- 可选快速通道：未经人工审查，可能误报；未经验证发现不适用 90 天披露期。

## 投递问题

首批报告大多被退信（推测邮件过滤器把 PoC 当恶意软件）；有密钥的已改发加密报告。正在试点经 GitHub Security Advisories 投递；FAQ 修订后最常见拒因是许可证不属于开源许可证。

申请数 / 接收数 / 投递问题来自 Punit Shah X 线程；官方说明页（10-13 更新）未收录这些数字。

## 评估（原文）

报告供给增加后，维护者的复现、去重与修复能力成为瓶颈；需同步准备分诊流程，否则大量报告只会积压。
